# 8、如何不花钱提升节点速度？零成本榨干VPS潜力的调优宝典

很多自建节点的朋友在遇到网速慢、卡顿转圈时，第一反应往往是：“是不是我买的这台 VPS 太便宜了？我是不是得加钱升级到高配套餐？”

别急着掏钱包！
事实上，**绝大多数海外 VPS 的网速慢，根本不是硬件配置不行，而是 Linux 系统的默认网络参数太保守了！**

Linux 系统最初是几十年前设计的，它默认保留了针对老旧慢速网络的保守参数（默认 TCP 缓冲区很小、默认拥塞算法极其胆小怯懦）。这就好比你买了一辆能跑 200 迈的高性能跑车，但出厂时发动机被系统偷偷锁死在经济慢速模式，油门只能踩下三分之一。

本文将教你用完全免费、不需要多花一分钱的几个系统调优大招，**仅仅修改几行参数，就能让现有节点的实际下载速度瞬间暴涨 3 到 10 倍！**

---

## 一、核心大招一：一键开启 Google BBR 拥塞控制算法（立竿见影之王）

如果整篇教程你只想做一个操作，**那就一定要开启 BBR**！这是整个互联网公认的“白嫖神技”。

### 1. BBR 到底神奇在哪里？（大白话比喻）
- **传统老算法（Cubic / Reno）**：前面讲过，传统的算法极其胆小。跨洋网络路上哪怕只掉了一粒小石子（丢包 1%），它就误以为整条高速路全塌方了，立刻一脚把刹车踩死，发包速度直接断崖腰斩；
- **Google BBR 算法**：Google 顶级天才工程师们研发的全新算法。**它根本不理会偶然的轻微丢包！**它会像雷达一样实时探测这根光纤的最大真实物理吞吐容量。即使路面偶尔有颠簸丢包，BBR 依然能以最大马力持续高速往管道里推送数据！

```mermaid
flowchart TD
    subgraph 传统算法遇丢包
    A1[正常发送 100Mbps] --> B1[遭遇 1% 跨洋偶然丢包]
    B1 --> C1[恐慌性踩死刹车 -> 暴跌到 10Mbps]
    end

    subgraph Google BBR 算法
    A2[正常发送 100Mbps] --> B2[遭遇 1% 跨洋偶然丢包]
    B2 --> C2[无视丢包, 持续雷达测算最大水管 -> 维持 90Mbps+]
    end
```

### 2. 一分钟开启实操
现在的 **Debian 11/12** 和 **Ubuntu 20.04/22.04/24.04** 系统内核已经自带了官方 BBR，你只需要一条命令把它唤醒：

在你的 VPS 终端中，直接复制粘贴以下代码回车：

```bash
# 写入 BBR 官方参数到系统配置中
cat << 'EOF' > /etc/sysctl.d/99-bbr.conf
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
EOF

# 立即刷新生效
sysctl --system

# 验证是否成功开启
lsmod | grep bbr
```

**看检验结果**：
如果终端屏幕上输出了带有 **`tcp_bbr`** 的字样，恭喜你，BBR 已经成功在底层开始狂飙！此时去 YouTube 测一下视频缓冲速度，你会发现速度瞬间翻了几倍！

## 二、核心大招二：扩大系统 TCP 读写缓存（把水管口径彻底扩宽）

在长距离跨洋网络中（高延迟、大带宽），网络学术界称之为“长肥管道（Long Fat Network）”。
如果系统默认的收发水桶太小，数据包在水桶里装满了就必须停下来等排空，这会导致严重的排队限速。

我们需要通过以下参数，把 Linux 的网络读写水桶扩大到 32MB~64MB：

在终端中执行：
```bash
cat << 'EOF' > /etc/sysctl.d/99-speed-tuning.conf
# 增大最大系统读写缓冲区
net.core.rmem_max = 67108864
net.core.wmem_max = 67108864
net.ipv4.tcp_rmem = 4096 87380 33554432
net.ipv4.tcp_wmem = 4096 65536 33554432

# 启用 TCP 窗口缩放支持与时间戳防丢
net.ipv4.tcp_window_scaling = 1
net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_sack = 1

# 提高系统网络最大并发连接等待队列
net.core.netdev_max_backlog = 10000
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 8192
EOF

# 让配置立刻生效
sysctl --system
```

## 三、核心大招三：客户端关键设置微调（避免本地给服务器拖后腿）

很多时候服务器速度很快，但本地客户端设置不合理，白白损耗了性能：

### 1. 开启“规则分流模式”，坚决不用“全局模式”
很多新手习惯开“全局代理（Global）”，这会导致你本地的微信、百度、爱奇艺全都在走海外节点绕一圈，不仅大量浪费海外节点流量，还会导致国内应用卡顿，甚至挤占节点带宽。切换为**“规则分流（Rule / 配置模式）”**，让国内直连、海外走代理，互不干扰！

### 2. 客户端开启“Fake-IP”解析模式
在 Clash Verge Rev 或小火箭等高级客户端中，DNS 模式推荐勾选 **`fake-ip`**。
- **大白话原理**：传统模式下，你每点一个海外链接，电脑都要停下来向海外等几百毫秒询问真实 IP；而 Fake-IP 模式下，客户端立刻给浏览器回一个本地假 IP，让浏览器瞬间启动连接，真正的数据在后台并行解析，使网页开启速度快上一大截！

### 3. 日志等级调为 `warning` 或 `silent`
如果你的客户端一直在高频打印所有请求的 `info` 或 `debug` 日志，大文件下载时疯狂写硬盘日志会直接吃满本地 CPU 资源。将日志等级设为仅警告，可以显著降低客户端卡顿。

## 四、优化效果前后自检对比

调优完成后，你可以通过以下指标检验成效：
1. **看 YouTube 详细信息统计**：
   在 YouTube 视频上右键点击“详细统计信息（Stats for nerds）”，观察 **Connection Speed（连接速度）**：
   - 优化前：可能只有 8,000 ~ 15,000 Kbps；
   - 优化后：直接飙升到 50,000 ~ 120,000 Kbps（提升 3~8 倍）！
2. **观察缓冲条长度**：
   优化前缓冲进度条只能往前走几秒钟；优化后视频刚一点开，灰色缓冲条直接瞬间冲到最右侧，彻底告别卡顿转圈！

## 五、常见高频问答 (FAQ)

> 💡 **排查指南**：自建节点若遇延迟高或阻断，可使用 [在线 IP 与网络测试工具](/notes/cheping/study/iptest/) 排查；线路挑选参考 [VPS行业黑话指南](/notes/cheping/study/vpscant/)，机场推荐可参阅 [神行加速全面深度测评](/notes/cheping/reviews/shenxing/)。

### Q1：开启 BBR 加速会对我的 VPS 稳定性有负面影响吗？
**答**：绝对不会！BBR 是由 Google 官方主导研发并已经被直接合并进 Linux 官方内核的核心标准拥塞算法。全世界数以亿计的 Google 搜索服务器、YouTube 视频 CDN 都在全天候稳定运行 BBR。它不仅不会破坏系统，反而能让服务器在网络波动时保持最稳健的传输表现。

### Q2：有些一键脚本里有“BBR 原版”、“BBR魔改版”、“BBR Plus”，小白该选哪一个？
**答**：**强烈建议只选择系统自带的“原版 BBR”！**
早期 Linux 旧系统因为没有原生 BBR，社区有人通过修改旧内核代码制作了各种魔改版。但是这些第三方魔改版很容易导致系统频繁死机、内核崩溃（Kernel Panic）或者断网失联；而现在 Debian 11/12、Ubuntu 22.04+ 自带的原版 BBR 已经演进得极为成熟稳定，完全不需要冒着死机风险去安装非官方魔改版。

### Q3：既然 BBR 这么神奇，为什么很多 VPS 厂商出厂不默认开启？
**答**：因为云服务商（如搬瓦工、AWS、甲骨文等）提供的 Linux 系统镜像是通用的官方精简模板，为了兼容各种古老的局域网应用或纯离线计算任务，出厂时默认维持最保守的经典设置，留给管理员根据具体业务场景自行开启。

### Q4：优化之后如果白天速度快，但晚上还是只有几兆，这是为什么？
**答**：BBR 能够做到的极限是**“把这条路现有的最大通行潜力完全榨干”**；但如果晚高峰期间，运营商直接把整条出海跨洋大门彻底堵死、整条骨干网丢包率超过了 40%，就算神仙算法也无法无中生有凭空创造带宽。遇到这种情况，说明瓶颈已经不是软件调优能解决的了，只能换用 CN2 GIA/AS9929/IPLC 专线 VPS。
